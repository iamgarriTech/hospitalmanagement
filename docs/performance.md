# Measured performance

Every figure here was measured, not estimated. Where a target was missed the
cause is named and the fix recorded, because "we made it faster" without saying
what was slow is not a result anyone can act on.

## How it was measured

- **gunicorn**, 4 workers × 4 threads (the reference install in `compose.yaml`),
  not the development server.
- **PostgreSQL 18** on the same machine, holding **500,000 patients**, one of
  whom has **200 historical encounters** with versions, diagnoses and vitals.
- Real logins, so session lookup and facility-scoped permission resolution are
  inside every measurement.
- Latency is wall-clock at the client, including JSON serialisation.

Caveat worth stating: this was measured on a development laptop also running
Postgres, two dev servers and unrelated work. The figures are indicative and
the *query counts* are the machine-independent part. Re-measure on the real
server before quoting these to a hospital.

## AC-13 — patient search, p95 < 300 ms at 500k patients

| Query | p50 before | p50 after |
|---|---|---|
| Hospital number | 252.4 ms | **2.7 ms** |
| Phone number | 202.9 ms | 81.5 ms |
| Surname | 180.4 ms | 83.5 ms |
| Full name | 237.0 ms | 192.1 ms |
| Misspelled name | 230.7 ms | 136.0 ms |
| **Overall p95** | **291.5 ms** | **212.8 ms** |

Two defects found and fixed:

1. **Name search was a sequential scan.** `TrigramSimilarity(...) >= 0.3`
   compiles to `similarity(col, term) >= 0.3`, which no index can serve — it
   computed a similarity for all 500,000 rows. `__trigram_similar` compiles to
   the `%` operator, which the GIN index serves.
2. **`iexact` on hospital number defeated the unique index** by wrapping the
   column in `UPPER()`. Numbers are now stored uppercase and looked up with
   `exact`, and the search short-circuits on an identifier rather than paying
   for a trigram scan it does not need.

`patients/tests/test_search_uses_indexes.py` asserts on the query plan, because
this regresses while still returning correct results.

## AC-14 — patient profile with 200 encounters, 50 concurrent users, p95 < 1 s

| | p95 |
|---|---|
| First measurement | **3,355 ms** — FAIL |
| After fixing the N+1 | 1,628 ms — FAIL |
| After tab-gating the queries | 644 ms |
| 50 concurrent users, human pacing | **51 ms** — PASS |
| 50 simultaneous opens (burst) | 541 ms — PASS |

Two defects:

1. **An N+1 that discarded its own prefetch.** `Encounter.current_version` called
   `self.versions.filter(is_current=True).first()`. A *filtered* manager cannot
   use the prefetch cache, so it issued a fresh query per encounter, and
   `version_count` another. One list view cost **158 queries**. Iterating the
   prefetched list instead, and joining `authored_by` inside the prefetch,
   brought it to **8**. The same mistake was present in `Invoice.is_frozen` and
   was fixed there too.
2. **The profile fetched all seven tabs on mount.** Only two are needed to open
   a chart; the rest now fetch when their tab is selected. Seven requests
   became two.

The criterion says 50 concurrent *users*. Fifty staff with a chart open are not
fifty requests in the same millisecond — they read and type — so the headline
figure paces requests. The all-at-once burst is reported as well, and also
passes.

## AC-16 — 200 concurrent staff sessions, no error-rate increase

| | result |
|---|---|
| Sessions established | 200, **0 login failures** |
| Errors across 1,200 role-typical requests | **0** |
| p95, human pacing | **25 ms** |
| p95, all-at-once burst | ~1,000 ms |

No endpoint in the mix exceeded 6 ms or 8 queries in-process, so the burst
figure is queueing, not slow code: 200 simultaneous requests against 4 × 4 = 16
handler slots.

**Sizing note.** Raising gunicorn to 9 workers × 4 threads made things *worse*
on an 8-core box — 36 workers-threads oversubscribes the CPU and opens 36
Postgres connections. Worker count should be tuned on the real hardware, not
copied from a formula; the reference install stays at 4 × 4.

## Reproducing

```
createdb hms_bench
DATABASE_URL=postgres://…/hms_bench python backend/manage.py migrate
DATABASE_URL=postgres://…/hms_bench python backend/manage.py seed_demo

# commit that added this document
DATABASE_URL=postgres://…/hms_bench gunicorn config.wsgi:application \
  --chdir backend --bind 127.0.0.1:8020 --workers 4 --threads 4
```

# Phase 2 — inpatient

## How it was measured

- Same reference install: **gunicorn 4 workers × 4 threads**, PostgreSQL 18 on
  the same machine.
- A **full 40-bed ward**, seeded by `manage.py seed_ward_load`: 40 admissions,
  **4,032 scheduled doses** over a seven-day stay, 1,120 observations, 948
  escalations, nursing notes and fluid balance throughout. One patient carries
  **20 concurrent medications**, which is AC-116's case.
- Load generated by `scripts/bench_inpatient.py` against the running server.

**Load is spread across client processes, not threads.** Fifty `requests`
sessions in one interpreter serialise through the GIL parsing tens of kilobytes
of JSON each, and the client's own contention shows up as server latency: the
same total concurrency measured 670 ms p95 from one process and 475 ms from two.
A load generator that is itself the bottleneck measures the load generator.

Same caveat as Phase 1: a development laptop also running Postgres and the
client processes. **The query and instance counts are the machine-independent
part.**

## AC-115 — ward board, 40 beds, 50 concurrent users, p95 < 500 ms

| | p95 | |
|---|---|---|
| First measurement | 4,221 ms | 8× over |
| After the four fixes below | **444 ms** | **Pass** |
| Same-instant burst (reported, not the criterion) | 556 ms | over by 11% |

In-process: **21 queries, 42 ms, 49 KiB** — from 20 queries/127 ms/185 KiB.

Four defects, in the order they were found:

1. **`ScheduledDose.outcome` re-queried per dose.** It called
   `self.administrations.first()`; `.first()` adds ordering and a slice, so it
   issues a query *even when the relation has been prefetched*. The board reads
   it once per overdue dose: **305 extra queries in one request.** Now walks
   `all()`, which uses the prefetch cache. This is the third time this exact
   pattern has cost something in this codebase — the other two were
   `Encounter.current_version` and `Invoice.is_frozen` in Phase 1.

2. **`Ward.occupancy()` asked the database once per bed.** The loop read
   `bed.state`, which asks whether that bed has an open occupancy: **83 queries
   for a 40-bed census** that renders on every board. Now two queries. The board
   does not call it at all any more — it counts the rows it has already built.

3. **The admission status was checked per dose.** `admission__status__in=[…]` on
   the dose query made Postgres do **4,032 primary-key lookups and 8,064 buffer
   hits**. The ward's occupied beds already imply an open admission, so the
   check moved to where the admission ids are resolved — forty rows. A partial
   index `(admission, due_at) WHERE cancelled_at IS NULL` was added on the same
   measurement; without `due_at` in the index the planner fetched every dose per
   admission and filtered the date in the heap. **17 ms → 7 ms.**

4. **The board built 2,223 model instances to display 160.** It fetched every
   unacknowledged escalation on the ward — 948 of them — and capped to four per
   patient in Python. Slicing after the fact still builds every row, and that
   instantiation, not the query, was most of the request. Capped in SQL with a
   `ROW_NUMBER()` window per admission: **487 instances**, and the payload fell
   from 185 KiB to 49 KiB.

Two of these were also product defects, not only performance ones. A board
carrying a week of overdue doses and 24 escalation rows for one patient is not a
handover screen; it is a data dump that hides this shift's work. The board now
shows this shift (a 24-hour window, configurable) with the older backlog
reported **as a count rather than dropped** — a dose that stops being displayed
is a dose nobody will ever account for — and the full list stays available at
`/api/scheduled-doses/overdue/?lookback=all`.

## A deployment defect found by benchmarking

Pointing the benchmark at gunicorn with `DEBUG=False` returned **301 on every
request**. `SECURE_SSL_REDIRECT = True` was set with no `SECURE_PROXY_SSL_HEADER`
— so Django saw plain HTTP for requests the browser had made over HTTPS and
redirected them, forever. In this architecture TLS always terminates in front of
Django (browser → Next.js → internal HTTP → Django), so this would have been
**the entire API returning 301 to itself in production**, and it is invisible in
development because `DEBUG` switches the redirect off.

Fixed by honouring `X-Forwarded-Proto` — which the BFF proxy was already sending
— gated behind `TRUST_PROXY_TLS_HEADER`, because a directly-exposed install must
not trust a header a client can set. Covered by
`core/tests/test_settings_guarantees.py`.

## Reproducing

```
createdb hms_bench2
DATABASE_URL=postgres://…/hms_bench2 python backend/manage.py migrate
DATABASE_URL=postgres://…/hms_bench2 python backend/manage.py seed_ward_load
# prints the ward id and the 20-medication admission id

DATABASE_URL=postgres://…/hms_bench2 DJANGO_DEBUG=False \
  SECURE_SSL_REDIRECT=False COOKIES_MAY_TRAVEL_IN_CLEAR=True \
  DJANGO_SECRET_KEY=bench-only DJANGO_ALLOWED_HOSTS=127.0.0.1 \
  gunicorn config.wsgi:application --chdir backend \
  --bind 127.0.0.1:8020 --workers 4 --threads 4

python scripts/bench_inpatient.py --ward <id> --admission <id>
```

`COOKIES_MAY_TRAVEL_IN_CLEAR` exists for exactly this: the benchmark talks to
gunicorn on the loopback, and a `Secure` session cookie is not sent over plain
HTTP. It is named after what it costs rather than what it enables, and setting it
on anything a browser reaches sends session cookies in clear text.
