# Security policy

VitaCore is intended to run real hospitals and hold real patient records. A
vulnerability here is not an inconvenience — it is somebody's medical history.
Please treat it accordingly, and we will too.

## Reporting a vulnerability

**Do not open a public issue.** Use GitHub's private reporting instead:

> Security → Report a vulnerability, on this repository.

If that is unavailable to you, open a public issue containing *only* the words
"security report, please make contact" and no detail, and a maintainer will
arrange a private channel.

Please include, as far as you can:

- what an attacker can do, in one sentence
- the steps to reproduce it, against a `seed_demo` installation
- the version or commit you tested
- whether you believe it is being exploited anywhere

You will get an acknowledgement within **3 working days** and an assessment
within **10**. If a fix is going to take longer than that, you will be told why
and when to expect it.

We will credit you in the release notes unless you ask us not to.

## What is in scope

- Anything that lets one user read, alter or delete another facility's data
- Anything that lets a user act beyond the permissions their roles grant
- Anything that alters or removes audit rows through the application
- Anything that exposes a session credential to JavaScript
- Authentication and session handling generally
- Injection of any kind: SQL, template, HTML, header, log

## What is out of scope

- Anything requiring a compromised database superuser. Somebody with `psql` as
  the owning role can do anything; the audit trigger and the reduced
  application role narrow the blast radius but cannot stop them.
- `DEMO_MODE=1`. It hands out working credentials on purpose. Running it in a
  real deployment is a misconfiguration, and the deployment checks refuse to
  pass with it on.
- Missing hardening on a development server run with `DJANGO_DEBUG=1`.
- Denial of service by volume against an installation you do not own.
- Reports generated by a scanner with no demonstrated impact.

## Deploying this safely

Read [docs/operations.md](docs/operations.md) before running it anywhere real.
The parts that matter most:

- `DEMO_MODE` **off**, `DJANGO_DEBUG` **off**, a real `DJANGO_SECRET_KEY`.
- Run the application as `APP_DATABASE_URL`'s reduced role, not the owner. That
  role cannot `UPDATE` or `DELETE` the audit log — which is what makes the
  audit trail worth having.
- TLS terminated in front of the app, with `TRUST_PROXY_TLS_HEADER=1` set only
  when a proxy you control actually sets `X-Forwarded-Proto`.
- `manage.py check --deploy --fail-level WARNING` must pass. CI runs it.
- A restore drill you have actually performed, not a backup you have never
  restored.

## Supported versions

Pre-1.0. Security fixes land on `master` and are not backported. Track the
default branch.
